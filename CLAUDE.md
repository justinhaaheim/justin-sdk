# justin-sdk

Cross-project SDK: one implementation of the tooling that would otherwise be copy-pasted into ~12 repos and drift. See `README.md` for usage, and run `justin-sdk agent` for the full agent playbook.

Validation bar here is home-base's own `bun run signal` — `tsc --noEmit`, eslint and prettier all cover this directory (home-base-dchjw.13, 2026-09-18) — plus `bun test`. This package has no eslint config of its own because home-base's applies; `tsconfig.json` here EXTENDS `templates/configs/tsconfig.node-cli.json`, the strict config the SDK ships to consumer repos, so the gate it hands out is the gate it meets. 64 files are still listed by name in home-base's `eslint.config.js` ignores while their remaining findings are worked down. **Run `bun test` with the Claude Code Bash sandbox OFF:** under the sandbox mise cannot write `~/.local/state`, and ~18 sweep/setup-env tests fail for that reason alone (measured 2026-09-10).

## Shape

- **Components follow npm's shape** (2026-09-18, epic `home-base-dchjw` D3), and the split is load-bearing: `add`/`remove` edit the MANIFEST (`justin-sdk.config.json#components`), `install` makes the DISK match it, `update` = pin bump + `install`. `init` enrols a repo (config + devDependency + shared scripts) and installs **nothing**. `list` prints every component with its purpose and its three independent states here: installed / applies / in the config. `core` is the only preset and is COMPUTED — every component whose `includeIf` passes in the repo you run it in; `add --help` prints that expansion for the current repo. An absent `components` key means `core`; `base-setup` is implicit and never listed. Default is **no commit** — files change in the working tree so the diff can be inspected first.
- **`install` NEVER removes** (dchjw.17 F1, 2026-09-18). It adds what the config lists and the repo lacks, re-applies the rest, and NAMES anything on disk the config does not list — then keeps it. `componentInstalledEvidence` reads generic filenames and value-matched lines, which is evidence, not provenance: measured on home-base's own committed config (`install --prune --dry-run`, 2026-09-18), the removing version of `install` would have deleted 14 `.gitignore` lines — `.claude/worktrees/` among them, which this repo requires on three surfaces — plus `.prettierrc.json`, `.prettierignore` lines and package.json scripts. Removal is `remove <name…>` or `install --prune`, and **`install --prune --dry-run` prints the full plan** — each path, line, script, hook entry and config key with its verdict — from the same code path that does the removing (`removeComponent(root, name, {dryRun: true})`), so the preview cannot drift from the act. No SDK caller passes `prune`: not the sweep, not `update`, not doctor's advice.
- **`remove` and `install --prune` delete by IDENTITY, never by name** (constraint F7). A file goes only when its bytes equal what the component would write right now; an appended entry (script, ignore line, hook, `componentConfig` block, `lint-staged`) only on an exact value match; everything else prints `left in place (modified): <path>` and survives. Content that cannot be reconstructed — `.beads/`, the generated rules artifact, a composed `.husky/` hook — carries `pristine: null` in `src/component-manifest.ts` and is NEVER deleted, only reported as `left in place (content not reconstructible)`. **There is no `--force` on `remove`, and adding one would be a mistake**: it would turn "I could not verify this" into "delete it anyway", which is the hazard the whole design removes. A `componentConfig` block is under the same rule as a file: only the untouched seed is deleted, so a tuned `gapHours`/`enabled: false`/`wrapUpAt` survives a reconcile that drops the component. Manifest drift fails SAFE in every direction (a stale expected value stops matching, so nothing is deleted), which is why the expected values are imported from the installers rather than retyped. A HOOK is under it too: `OwnedHook` carries both a `fingerprint` (finds the hook in any generation of spelling) and the exact `command` the installer writes today, and only `command === ours` is deleted — `bun run justin-sdk time-check && my-own-thing` is half a person's and is reported modified. `OwnedScript.shared` marks a key that is **not this component's alone** — never evidence of an install, never removed: the `signal-source:*` trio is base-setup's (it seeds all three into every enrolled repo), and `prebuild` / `eas-build-post-install` run version-manager, which non-Expo repos use on its own. Both were found by running `list` against home-base; each would otherwise have made `install` delete something real.
- **`check-runner`** is an importable module (`@justinhaaheim/justin-sdk/check-runner`), not a copied file. Checks support `severity: 'warn'` (non-blocking) vs `'error'`, and accept shell commands or TypeScript functions. Every byte of a tree run's stdout goes through an `OutputSink`, so `runCheckTree` prints as it goes while `renderCheckTree` hands the same report back as a string — which is how `doctor` has both `runDoctor` (prints) and `renderDoctor` (returns). `session-start` uses the latter: stdout there belongs to the JSON envelope, and it used to be protected by monkey-patching `console.log` AND `process.stdout.write` (both, because in Bun they are independent channels). ANSI is stripped from `additionalContext` only — it goes to the model, while `systemMessage` goes to a terminal.
- **Doctor's fix advice is rewritten to be runnable in the repo it is printed for.** Where `<root>/node_modules/.bin/justin-sdk` is absent, every `bun run justin-sdk …` in a `fix`/`fixCommand` gains a `bun install && ` prefix — otherwise the advice fails with `error: Script not found` in exactly the checkouts (fresh worktree, fresh clone) where doctor has the most to say. Applied once, in `withRunnableFixes`, so a check added later gets it for free; the `bunx github:` bootstrap form is deliberately untouched, since needing no node_modules is its whole point.
- **`signal` and `doctor` discover their work from the consumer's package.json** — `signal-source:LABEL` and `fix-source:LABEL` scripts. That keeps per-project variation in the project, not in a forked script.
- **`doctor` fixes scaffolding** (configs, deps); **`fix` fixes code** (eslint --fix, prettier --write). Keep them distinct — formatting is never auto-run at session start.
- **Health notices** (`src/health-notices.ts`) gate two probes — "a newer justin-sdk exists" and the doctor heartbeat — behind one set of tiers, throttles, config and state. `justin-sdk config schema` prints every knob; `JUSTIN_SDK_HEALTH_NOTICES=off` silences them for one invocation, and any child justin-sdk you spawn must carry `silencedChildEnv`.
- **`sweep`** propagates a component across all enrolled repos, each in its own temp worktree with gates and a push. Its doctor/signal gates are a **ratchet**: each is measured before AND after the payload, and only green→red fails (home-base-ckc4). A red step removes its worktree and writes the evidence to `~/Dev/home-base/tmp/sdk-sweep/<run>.log`. Its gates run `<worktree>/node_modules/.bin/justin-sdk` **by path** and refuse when it is absent — `bun run justin-sdk` there falls through to a PATH shim on a half-failed install and gates the repo against the orchestrator's SDK. `--component` picks the payload: a component name (pin untouched), `install` (the ENROLLMENT REFRESH — adopt installed-but-unlisted components into the config, delete the dead `version`/`lastSynced`/`modules` keys, bump the pin, then `install` with **removals disabled**), or absent for the historical pin-bump-and-re-apply-all. **A sweep never removes a component**: a config listing fewer than the disk is the SDK's own history, not a decision, so removal stays a per-repo `remove`.

## Design principles

- **No hidden side effects.** Doctor checks warn, they never auto-fix. Auto-`bun install` at session start was rejected even at 70–250ms.
- **Write actions need a trigger, not a heartbeat.** Local `setup-env` runs at worktree creation and manual invocation only; remote runs at session start.
- **Every module must be independently complete.** Per-repo module selection means no module may lean on a sibling being present.
- **`--quiet` shows a one-liner on all-pass**, and only errors/warnings on failure.
- **Every JSON the SDK writes is prettier-formatted immediately, with the target repo's own prettier** — resolved from the repo's local `node_modules/.bin/prettier`, silently skipped when absent. Tool output must be idempotent, and most repos run prettier on commit. Local-binary-only on purpose: a `bunx prettier` fallback hit the registry on every write and blew the test suite past 120s.
- **Emit `justin-sdk` in all text, docs, aliases, and error messages.** The `j` and `jsdk` bins are GONE (removed 2026-09-18, epic `home-base-dchjw` D1) — both names resolve to real, unrelated npm packages, so every `bunx j`/`bunx jsdk` was a live hazard.
- **`session-start`'s `systemMessage` no longer echoes the full prime injection** (dchjw.17 F9). It is a ONE-LINE status header — `justin-sdk session-start · <parts>` — plus, when there is something to act on, the rules-drift advice. The old per-repo hook printed the whole injected rules text there; that is `additionalContext`'s job (the model reads it), and `systemMessage` goes to a terminal for Justin. If someone reports "the rules stopped appearing at session start", the header's `rule text NOT injected (this repo carries its own)` marker is the answer, and it is deliberate: an enrolled repo has its own committed artifact.
- **Session start is ONE command, `session-start`, and two hooks that never both act** (D6, 2026-09-18). The `prime` Claude Code plugin, its marketplace and its vendored `src/plugin` copy of prime + repo-status are GONE: it was a separately-versioned second implementation that sat 178 commits stale for a month, twice, with nothing detecting it. `src/session-start.ts` does the work (remote → `setup-env`; local → `doctor --quiet` + the repo-state block + the rules-drift notice, as one SessionStart JSON envelope). The project hook base-setup writes runs `bun run justin-sdk session-start`; the user-level hook in `~/.claude/settings.json` runs `justin-sdk-latest session-start --user-level`, which exits 0 printing NOTHING when the project root carries `justin-sdk.config.json`. So the repo-state block still reaches every repo, enrolled or not. **The SDK never writes `~/.claude/settings.json`** — the `USER_LEVEL_SESSION_START` doctor check warns and prints the exact JSON (it lives in `src/user-level-hook.ts`, with the guard in the hook string so an enrolled repo never spawns the network path); pasting it in is a human step.
- **There are exactly three invocation forms (D1), and `src/sdk-invocation.ts` is the only place they are spelled.** `justin-sdk <cmd>` inside a package.json script VALUE; `bun run justin-sdk <cmd>` for hooks, advice strings, docs, fixCommands and anything the SDK spawns (hooks run under `sh`, so the prefix must be written out); `bunx github:justinhaaheim/justin-sdk <cmd>` for BOOTSTRAP only — the remote SessionStart branch and enrolling a repo that has no `node_modules` yet. Everything else is retired, and `install` rewrites it: `bunx @justinhaaheim/justin-sdk` and the bare `bunx justin-sdk|jsdk|j` all fall through to the public npm registry when local resolution fails (`home-base-2qhw`), and an unpinned `bunx github:` outside bootstrap is cached by SPEC STRING and silently serves whatever it first fetched.
- **A consumer pin is verified against the remote before it is written** (`stepDepsHasSdk`, `home-base-l9tz`). A dev checkout whose version was bumped but never released would otherwise pin every consumer to a 404. Confirmed-absent refuses; an unreachable remote writes the pin and says loudly that it could not be checked.

## Gotchas

- **This directory IS the SDK. It is `home-base/pkg/justin-sdk`, a bun workspace member — not a submodule and not a separate repo** (folded in 2026-09-18, epic `home-base-dchjw` D5). Commit here like anywhere else in home-base; there is one branch and one beads DB. `github.com/justinhaaheim/justin-sdk` is a **distribution channel**: it receives snapshots and is never edited directly.
- **Release with `bun run sdk:publish` from home-base, and nothing else.** It is the whole release in one command — version bump, home-base commit, snapshot, `vX.Y.Z` tag, push, and the cache clearing below. `--dry-run` writes nothing anywhere; `--bump minor|major` when a patch is not right. Do NOT hand-roll `git tag` + `git push` against the published repo: the publisher refuses when that repo moved without home-base, and hand-pushing is exactly what trips it.
- **The FIRST release after the fold-in needs `--first-publish`, and only that one.** `pkg/justin-sdk/.last-published.json` does not exist yet, so nothing here records what the published repo holds — and a snapshot replaces its whole tree. With no record the publisher refuses (under `--dry-run` too) and prints the published HEAD so you can look at it first; `--first-publish` is you saying the replacement is intended. The run writes the record, so every later release goes back to the plain command. **Run it with the Claude Code sandbox OFF** — it runs the SDK's whole `bun test` first and any failure refuses the publish, and sandboxed ~18 of those tests fail on tempdir EPERM alone.
- **Publishing needs no permission** (Justin, 2026-09-07). Run it whenever the work calls for it, rather than asking and stopping.
- **Consumers pin tags, so a version bump without a pushed tag changes nothing for them.** `sdk:publish` always does both, which is the point of having one command.
- **`sdk:publish` also clears two caches, and doing it by hand skips them.** The health-notices probe caches its last remote tag lookup for `checkIntervalMinutes` (60 by default), so a release you just pushed goes unnoticed for up to an hour — including by your own repos (home-base-uxwc.4). The bunx spec cache is the same story.
- **Prefer `v`-prefixed tags.** With both `0.14.0` and `v0.14.0` present, `pickLatestTag` breaks the tie by gh API ordering — which tree you get is nondeterministic.
- **`bun test <path>` is a cwd-relative filter, not a path.** Run from the wrong directory it silently matches a different checkout's copy of the tests. Verify cwd before trusting a green run.
- **In a Claude Code session, the full `bun test` needs the sandbox OFF, and so does every git write from a `.claude/worktrees/` checkout** (measured 2026-09-12, home-base-a1go). Sandboxed, 18 sweep/hydration/pin tests fail on `bun is unable to write files to tempdir: EPERM` — a sandbox artifact, not a red suite; single files usually pass sandboxed. Git writes from here are now ordinary home-base writes and work sandboxed — the old `Unable to create .../index.lock: Operation not permitted` failure was a submodule artifact (a worktree's submodule gitdir lived under the superproject's `.git/modules`, outside the sandbox allowlist) and went away with the 2026-09-18 fold-in. The e2e needs the sandbox off too (real sessions, the daemon, `~/.local/state`).
- **`bun install` runs NONE of the root package.json lifecycle scripts** — `preinstall`, `install`, `postinstall` and `prepare` are all skipped (measured, bun 1.4.0; npm DOES run them). So a repo that generates files from `postinstall` gets nothing from `setup-env`'s INSTALL step, and its fresh worktrees are missing those files. Hydration has to go through a `setup-env-source:<LABEL>` script or `.worktreeinclude`.
- **`bunx <pkg>` only resolves a local `node_modules/.bin` entry whose target is EXECUTABLE.** Without the exec bit it silently falls through to the registry — in a test fixture that turns a hermetic run into a network fetch whose 404 becomes the "measured" exit code.
- **Installers chain `base-setup`, which stamps the running SDK's version** — any in-process component run needs a pin-neutrality snapshot/restore guard so it doesn't bump pins as a side effect.
- **Run `bun run e2e:justin-loop` before every justin-loop release — it CANNOT run in CI.** `bun test` only ever drives the loop against a scripted fake `claude` and `br`; `scripts/e2e-justin-loop.ts` is the only thing that exercises the seams — a real `claude --bg` session finding `justin-sdk` on its PATH, `claude stop` clearing the row before the successor is dispatched, the handoff JSON surviving a real `br`. It needs a logged-in `claude` and spends real quota, so it is deliberately outside the suite. Every run records its artifacts under `tmp/e2e-justin-loop/<stamp>/<scenario>/`; `--replay <dir>` re-checks a recording with nothing spawned, which is how each assertion gets its negative control.
- **An `advisor` call's assistant records carry the SUM of every model turn inside them, not a context size** (measured 2026-09-12, home-base-fjcp). The sum double-counts `cache_read_input_tokens`, so the record reads ~2x the real context — 341,867 against a true 172,463, enough to fire a false wrap-up directive. The exchange is SEVEN records sharing one `message.id`, and the last one carries only a bare `tool_use` block, so filtering on content-block types does not catch it. The per-turn breakdown in `message.usage.iterations` is the fix: when it holds more than one entry, the LAST entry is the session's context as that record ended. Anything reading `message.usage` as a context size must go through `usage-check`'s `contextTokensFromRecordUsage`, the shared selector, rather than summing the top-level fields itself.
- **A subagent's transcript is a separate file, and every record in it says `isSidechain: true`** (measured 2026-09-04, 170/170 on a live player). It lives at `<transcript_path minus .jsonl>/subagents/agent-<agent_id>.jsonl`, and the `sessionId` INSIDE it is the PARENT's — identity is in the path only. Hook payloads carry `agent_id`/`agent_type` when and only when the tool call came from a subagent, so their presence is the role discriminant. `usage-check` uses all of this; anything else reading transcripts must not reuse a session-shaped sidechain filter, which would skip a subagent file entirely.
